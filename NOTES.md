# Notes

## Assumptions

- **No cost or rate data exists in the schema, by design.** Budget and spend are tracked; salaries, billing rates, and internal costs are not. This means profit margin, cost-per-hour, and true financial-risk ranking are all questions the tool should honestly decline rather than approximate from budget-vs-spend alone (which measures burn, not profitability). The grounding prompt enforces this, and it holds up consistently across all three AI endpoints (ask, brief, explain) — I tested it directly with "What's our profit margin per project?" and got a clean, specific refusal every time, including in production.
- **Row-Level Security is off for this demo.** Access control sits at the application login layer (all dashboard routes require an authenticated Supabase session via middleware), and every AI-facing read goes through the server-side service-role client, never the browser. In a real production deployment with real client financial data, I'd enable RLS with per-role policies rather than relying on the app layer alone — see "what I'd build next."
- **The Meridian Health / Meridian Healthcare duplicate is intentional and left unmerged.** It's meant to surface the kind of duplicate-entity mess a real agency's tracker accumulates over time (two account people, two spellings, same client). The Clients page deliberately shows them as two separate cards rather than silently deduplicating — fixing that quietly would defeat the point of the exercise.
- **The composite ordering score in the signal engine is a heuristic, not a risk measurement.** It's used only to sort the Attention Rail and Projects list; it's never shown to the user as a number, and the code comments it as such. I preferred explainable flags over a single opaque score.

## What gave me pause

- **A local TLS certificate error connecting to Supabase** (`UNABLE_TO_VERIFY_LEAF_SIGNATURE`), almost certainly from security software on my machine doing HTTPS inspection. Fixed by running Node with `--use-system-ca` so it trusts the Windows certificate store instead of its bundled one, baked into the `dev` script so it's automatic going forward. Purely a local dev-environment issue — it didn't appear on Vercel's infrastructure.
- **Next.js 16 renamed the `middleware.ts` convention to `proxy.ts`** mid-way through building auth, after my tooling's baseline knowledge. The fix required checking the current Next.js docs directly rather than assuming the older convention. A good reminder that framework conventions move fast enough that "I already know this" is worth double-checking even for things that feel settled.
- **The weekly brief truncated mid-sentence on the first generation attempt** — the token budget was too tight for how much the model wanted to say once given ten flagged projects to synthesize. Fixed by tightening the prompt to force real synthesis (name only the highest-priority items per section, not every flagged project) and raising the token ceiling. The fix produced a genuinely better brief, not just a longer one — it now reads like something a CEO would want in 30 seconds rather than a project-by-project dump.

## What I'd build next with more time

- **Trend detection.** The brief lists this as a "where AI should make it smarter" example, and I've deliberately left it out: the current data is a single point-in-time snapshot, and detecting a trend from one snapshot isn't meaningfully different from inventing one. I'd add periodic snapshots (even a simple daily table of computed signals) so the AI could genuinely compare this week to last week, rather than fabricate a trajectory.
- **Entity resolution as a real feature, not just a display quirk.** Right now the Meridian duplicate is correctly *surfaced* but not *resolved*. A natural next step is an AI-assisted "these two client records appear to be the same organization — merge for reporting?" flow, which is a stronger demonstration of AI-on-messy-data than simply not crashing on it.
- **Tool use instead of digest-in-context for the Ask endpoint.** The current approach sends a compact JSON digest of the whole portfolio on every request, which is simple and fast at this scale (10 projects) but won't scale gracefully to hundreds. I'd move to Claude calling scoped tools (e.g. `get_project(id)`, `search_projects(filters)`) against Supabase directly, so context stays small regardless of portfolio size.
- **RLS with real per-role policies** (e.g. a project lead sees only their own projects; leadership sees everything) for any real deployment with actual client data, rather than relying solely on the application-level login gate used here.
- **Automated proactive alerts**, distinct from the always-visible Attention Rail — e.g. a digest email when a project crosses a new threshold (newly over budget, newly stale), rather than requiring someone to open the dashboard to notice.
